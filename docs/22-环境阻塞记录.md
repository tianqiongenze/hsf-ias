## 2. 判读要点（为何误判"docker 栈僵死"）

- **k8s 与 docker 双栈并存（2026-11-14 R-10 实测修正）**：master/worker 均为 **kubeadm v1.28.2 + cri-dockerd +
  moby dockerd（runtime=docker://26.1.4，两节点一致）**，并非原文所判的"k3s containerd"。
  复测命令与输出：`kubectl get node -o jsonpath='{range .items[*]}{.metadata.name}{": "}{.status.nodeInfo.containerRuntimeVersion}{"\n"}{end}'`
  → `k8s-master: docker://26.1.4`、`k8s-worker1: docker://26.1.4`；master `docker ps --format '{{.Names}}'`
  中可见 250 个 `k8s_*` 容器（含 `k8s_gw_gw-659d76c75b-*_hsf-prod_*`，Up 时长与 kubectl AGE 吻合；
  hsf-timescale-0/hsf-mosquitto-0 位于 k8s-worker1，其容器在 worker1 的 dockerd 内——kubelet 只经
  cri-dockerd 起 pod，节点 runtime 版本即 pod 所在栈）。**含义：restart docker = 重启全部 hsf-prod pod，
  本项目工作负载与 dockerd 不是隔离关系。** 原"k3s containerd"判读系未核验 nodeInfo 的推断，保留作教训。
- **SSH 空闲掐流放大了卡死感知**：长无输出命令（docker build -q、docker info 大 catalog）在无 keepalive 会话上
  表现为"整条 SSH 挂死"。
- **dockerd Memory 10.5G（Tasks 60）**：大 catalog（166 镜像）+ 长运行 4 周，CLI 慢响应疑似 dockerd 内存/锁压力；
  未达到不可用程度（11-09 会话仍在同一 dockerd 上完成了 2.0/3.0 镜像构建推送）。

## 6. R-07 密钥轮换窗口事件：hsf-redis-0 被跨租户抢占（2026-11-14 18:20 UTC+8）

  `redis-cli -a $REDIS_PASS --cluster create <三 hostname> --cluster-yes` → `[OK] All 16384 slots covered`，
  `cluster_state:ok/16384/3 节点` 复核，ratelimit readyz 恢复 `{"ready":true,"backend":"redis-cluster"}`。
- **暴露的结构性风险（留档，修复归口阶段 3）**：① hsf-redis 无 PriorityClass（属 infra ns 既有部署，
  非本项目命名空间配额管辖）——跨租户抢占会静默重置集群（emptyDir 无持久化）；② ratelimit/gw 的

### 8.3 建议巡检项（巡检口径固化，复测窗口执行）

1. `conntrack -S`（master+worker1）：k6 运行**前后 diff** `insert_failed/drop/early_drop/search_restart` 增量；

4. `ip link show tunl0`（两节点）：MTU 一致性；
5. `sysctl net.netfilter.nf_conntrack_max net.netfilter.nf_conntrack_count`：容量余量。
