## 5. 性能验收

### 5.1 k6 基线（browse 200VU + report 20VU，登录改造版）

| 指标 | 一期终版基线（docs/20） | 二期实测 | 判据 |
|---|---|---|---|
| 失败率 | 0% | **0.00%（0/7368）** | <5% ✅ |
| browse p95 | 521ms（阈值 500，+4% 环境噪声留档） | **348.89ms** | ≤500ms ✅（较一期再优化 33%） |
| report p95 | 724.92ms | **103.69ms** | ≤800ms ✅ |
| med | 20.69ms | 28.04ms | — |
| checks | 100% | 100%（14296/14296） | — |

**基线脚本改造说明（§6.4）**：RATE_CAP=1200 固定窗口下无登录读流量全部聚合在单个 `ip:` 键（200VU≈4800/min 必 429，首轮实测 65.62% 失败率验证了该数学事实）——browse/report 改为**每 VU login-once**、登录号循环取自 04 §9.1 冻结 15 账号（200 VU → 15 个 `u:` 键，每键 ≈230~320/min < 1200）。改造后 0 失败复测通过；`40-k6.yaml` ConfigMap 与 `perf/baseline.js` 保持同源同步。

### 5.2 iot-write 时序吞吐（单独报告，不进 thresholds）

| 项 | 实测 |
|---|---|
| 负载模型 | 4 VU × 50 迭代 × steps=500（单迭代 2.4 万条），迭代间 sleep 5s |
| k6 执行 | 200/200 迭代全完成，367.3s，`iot_published`=2,183,515 条（sim tick 响应口径） |
| **TimescaleDB 落库** | **行数增量 ≈2,027,608 条（1009→2,027,617）** |
| **全链路吞吐** | **≈5,524 条/s ≥ 5000 参考目标 ✅**（sim 生成→MQTT→iot 缓冲→TimescaleDB） |
| tick 时延 | med=585ms / p95=8.29s（同步发布 2.4 万条 QoS1 的预期量级）；check 84%（32/200 超 k6 120s 兜底——sim 单副本同步发布背压，如实记录） |
| `onconflict_skipped` | 872,391（QoS1 重传/补投重复被 `uk_reading` 幂等拦截，D-07-3 设计预期；其中含 iot 排障期多次重启的 broker 离线补投重复） |

> **口径说明（W3-2 修复）**：首轮 iot-write 报告吞吐 4 条/s 为**指标假象**——`psycopg2.extras.execute_values` 内部分页执行会覆盖 `cur.rowcount`（仅剩最后页 ≤500 的计数），`written_total` 指标严重低估；真实落库以 **TimescaleDB 行数差值**为准（≈5500 条/s 达标）。W3-2 修复（iot:2.0.6 手动分页累计 rowcount）后指标与表行数口径一致。

## 7. 残余事项（如实记录）

1. **iot-write tick check 84%**：32/200 迭代超 k6 120s 兜底（sim 单副本同步发布 2.4 万条 QoS1 的背压特性，p95=8.29s）；吞吐判读以落库行数为准已达参考目标。三期可评估 sim 异步发布/分片。
2. **iot 单副本固定**（latest 缓存与回差状态机为进程内状态，D-07-1/A-07-3）：重启窗口由 broker `clean_session=false` 离线队列补投 + 数据库幂等兜底（本轮实测补投重复 87 万条全部被 `uk_reading` 拦截，零重复落库）。
3. **ResourceQuota limits.cpu 余量偏紧**（32C 配额 vs 一期 HPA+二期新组件动态占用）：后续扩容前需核对 `kubectl get resourcequota`；必要时扩配额走 ADR。
4. **browse p95=349ms 中 med=28ms**：长尾仍含共享集群噪声（master conntrack 租户压力，docs/20 §7 同源），但较一期终版（521ms）收敛 33%。
5. **真实硬件接入、遥感解译、全国平台对接**：三期范围（notCovered 延续一期口径）。
