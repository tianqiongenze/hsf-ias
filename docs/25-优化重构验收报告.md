**瓶颈归因（4-worker 对照实验结论）**：

1. **iot 刷写侧已解除瓶颈**：run3 全程 `hsf_iot_buffer_size` 恒 <2,000（run2 高峰 6,161、终态归零需要背压反灌 sim）——flush 侧不再绑定，输入即上限。
2. **sim 发布侧为全链路上限 ~2,900 条/s**：`iot_published` 速率 2,929.5/s（run2）/2,901.9/s（run3）两轮几乎一致，与 FLUSH_WORKERS 无关——sim 单进程 paho 同步 QoS1 发布（inflight=100）+4 VU 串行排队为结构上限；R-02 冻结"同步返回 published 条数"契约（docs/07 §2.5），异步化仅评估不实施（docs/24 §4 R-02）。二期 5,524 条/s 记录对应"DB 数百万行级+无共租户噪声"环境，不可直接对比。
3. **onconflict 153,162（8.3%）**：4 VU 并发 tick 的 `recorded_at` 毫秒步进碰撞（`services/sim/app/repo.py:117-120` base=now_local() 步进 1ms，并发 tick 时间窗重叠 → 同 (device_code, recorded_at) 幂等键冲突）——测试负载模型固有，非链路丢失（对账闭合证明）。
4. **环境噪声**：worker1 共租 ollama ~29.6 核常驻（`kubectl top nodes`：worker1 33,934m/53%）——R-23 已立案口径。

**对账等式（逐段）**：

- 第一段 sim→broker→iot：`publish_total Δ 1,848,412 − broker dropped 0 = received Δ 1,848,412`（**精确相等，差 0**；sim 侧 fail+retry 为发布器内部补偿闭环，重投成功已计入 publish_total）
- 第二段 iot 收→落库：`received Δ 1,848,412 = written Δ 1,695,188 + onconflict Δ 153,162 + buffer Δ 0 + buffer_dropped 0 + 在途残差 62`（残差 62 条 = 采样时点在途，占比 **0.003%**）

- **headline 等式：published 1,848,412 = written 1,695,188 + onconflict 153,162 + 丢弃 0 + 在途 62 ✓ 闭合**（替代 docs/23 §4.2 的"推断口径"，R-02 验收口径原文达成）

**R-04 teardown 直读验证**：k6 teardown 吞吐行非 0.0（2,614.0 条/s）且与 psql 表差值一致（630s 窗口 1,646,854 ≈ 表 1,695,188 的 630s 段），科学计数法解析修复在 ≥1e6 计数器下实测生效（171,661→1,769,213 全量正确解析）。
