## 5. 发现的问题

### 5.1 【P1】限流触发返回 HTTP 500 而非 429，验收用例 12 未达成

- 验收口径：docs/06:162 `| 12 | 限流触发 | 高频请求触发 429 | P1 | FR-705 |`；docs/06:192/210 同口径。
- 实现位置：`gw/gateway.js:90-95` —— context 中 `rateLimit(key)` 失败时 `throw err`（`err.extensions={code:'RATE_LIMITED'}`），注释"HTTP 状态由 Apollo 统一处理"；未做任何 429 状态映射。
- 实测（9000 并发突发打单 gw pod，`seq 1 9000 | xargs -P 30 curl …`）：
  ```
  4719 200
  4281 500        ← 限流触发响应为 HTTP 500
  ```
  触发响应 body：`{"errors":[{"message":"Context creation failed: 请求过于频繁，请稍后再试","extensions":{"code":"RATE_LIMITED","stacktrace":["... at context (/app/gateway.js:92:21) ..."]}}]}`
- 结论：限流**功能生效**（超量正确拒绝、错误码 RATE_LIMITED 正确），但 **HTTP 状态码 500≠429**，不满足 docs/06 P1 验收条款。修复建议：Apollo `willSendResponse`/`formatError` 阶段按 `RATE_LIMITED` 映射 HTTP 429，或改在 plugin 层短路响应。
- 附带发现（限流容量语义）：令牌桶为**进程内 Map**（`gateway.js:41`），每副本独立 cap=6000/min，且 `refill=RATE_CAP/60000=100 tokens/s`（gateway.js:43）。多副本（HPA max6）下集群级总容量 = 6000×副本数；100 tokens/s 的补充速率意味着 ≤100 req/s 的持续流量在数学上**永远打不穿桶**（E2E 串行约 40 req/s 即此情形；我方 6500 并发突发亦因 11s 内补充约 1100 未击穿）。验收测试需并发突发 ≥ (cap + 吞吐×时长) 才可复现。

### 5.2 【P2】k6 压测 p95 超阈值（browse 1.66s / report 1.83s vs 500ms/800ms）

- 失败率 0% 但 p95 长尾严重（med 44ms、p90 1.43s、max 3.86s），与压测窗口内 HPA 2→4 副本扩容滞后直接相关（§3.4 events 证据）；老 CPU 节点上 220VU 并发下服务 CPU 饱和。
- 建议：压测前预热扩容（minReplicas=4 起测）或延长 ramp 阶段消除扩容窗口后再测 p95；当前数据如实记录为首次基线。

### 5.3 【P3】E2E 脚本"一张图地块渲染"未注入页面登录态（用例设计缺陷）

见 §4.3 FAIL-1。修复建议：`e2e_browser.py` 用例 3 前执行 `page.evaluate("localStorage.setItem('token', ...)")`（与页面 doLogin 的存储键一致）或驱动页面登录表单后再断言。

### 5.4 【备注】测试基础设施

- pypi 直连在该网络不可用/极慢（37.9MB wheel 下载 9 分钟未完成），pip 需显式走内网可达镜像源；建议后续测试 Job 固化清华源参数。
- 集群侧 iam/land/project/facility 曾在压测前出现一轮 HPA 副本变化（3m37s AGE），无 CrashLoopBackOff，不影响结论。
